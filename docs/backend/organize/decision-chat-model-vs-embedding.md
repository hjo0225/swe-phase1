# 노트 자동 분류: 채팅 모델 방식을 쓰는 이유 (D-19)

- 날짜: 2026-10-03
- 상태: **채택** (구현 예정 — 지금 코드는 아직 임베딩 + 군집화 방식이다)
- 관련: PR #1 «노트 제목 뜻으로 자동 폴더 분류 (organize)», `docs/superpowers/plans/2026-10-01-organize-*.md`

## 결정

노트를 폴더로 나누는 일(«분류하기», 새 노트 자동 배치, `.md` 끌어다 놓기)을 **제목 임베딩 + k-means 군집화** 대신 **채팅 모델(LLM) 한 번 호출**로 한다.
노트 제목 목록(과 이미 있는 폴더 목록)을 주고, 노트마다 들어갈 폴더 경로를 구조화 출력(JSON Schema)으로 받는다.

## 왜 바꾸나

### 1. 임베딩 방식은 노트가 많으면 앱 전체를 멈춘다 (가장 심각)

멈춤의 원인은 임베딩 요청이 아니라(네트워크 호출이라 0.3~0.5초, 앱을 막지 않는다) 받은 벡터로 하는 **군집화 계산**이다.
묶음 수 k를 2부터 «노트 수 ÷ 2»까지 모두 시도하고(k마다 k-means 5번 재시작 + 실루엣 점수), 이 계산이 **Main 프로세스에서 동기로** 돈다.
그동안 자동 저장·IPC·화면 응답이 모두 멈춘다.

| 노트 수 | 군집화 계산 시간 (합성 벡터, 같은 알고리즘) |
| --- | --- |
| 100 | 0.9초 |
| 200 | 18초 |
| 300 | 79초 |
| 400~600 | 10분 안에 끝나지 않음 |

실제 API로 잰 «분류하기» 한 번의 멈춤 시간: 200개 12초, **600개 1,227초(20분 넘게 «응답 없음»)**.

### 2. 정확도도 채팅 모델 방식이 같거나 높다

같은 모델(`gpt-5.4-mini`), 같은 데이터로 두 방식을 비교했다.

| 노트 수 | 채팅 모델: F1 / 걸린 시간 / 멈춤 | 임베딩 + 군집화: F1 / 걸린 시간 / 멈춤 |
| --- | --- | --- |
| 100 | **85%** / 8초 / 0초 | 75% / 8.5초 / 2초 |
| 200 | **92~94%** / 13~15초 / 0초 (2회) | 83% / 19초 / 12초 |
| 400 | **85%** / 26초 / 0초 | **실패** — GPT 폴더 이름 단계가 쓸 수 없는 답을 돌려줌 |
| 600 | **89%** / 40초 / 0초 | 87% / 1,241초 / 1,227초 |

PR에 들어 있는 시험 데이터(`samples/organize-test-vault`, 노트 100개·정답 11개 주제)에서는:

- 임베딩 방식(`gpt-5.4-mini`): 순도 77~78% — 코딩 4개 주제는 정확했지만 찌개+파스타, 헬스+러닝이 합쳐지고 여행이 «생활/일정»에 기타 메모와 섞였다.
- 채팅 모델 방식(Kimi `kimi-k2.6`, 2회): **100% 일치, 두 번 결과 동일**, 28초. 폴더 이름에 오타 하나(«운동»→«울동»)와 «자료구조»를 «수학» 아래 둔 것 외에는 정답과 같았다.

### 3. 임베딩은 OpenAI에서만 된다

Kimi에는 임베딩 API가 없어(`KimiProvider.embed` → `UNSUPPORTED`) Kimi 사용자는 분류 기능을 쓸 수 없다. 채팅 모델 방식은 Blink가 지원하는 두 Provider 모두에서 된다.

### 4. 임베딩 방식의 장점은 지금 코드에서 살아 있지 않다

| 이론상 장점 | 지금 상태 |
| --- | --- |
| 노트가 수천 개여도 처리 | 군집화가 300개에서 79초, 임베딩 요청은 2,048개를 넘으면 실패 |
| 새 노트 배치는 제목 하나만 임베딩하면 됨 | 벡터를 저장하지 않아 매번 그 폴더 아래 노트 전부를 다시 임베딩 |
| 같은 입력이면 늘 같은 결과 | **유일하게 남는 장점.** 채팅 모델은 원칙적으로 흔들릴 수 있다(측정에서는 2회 결과가 같거나 F1 2%p 차이) |
| 비용이 쌈 | 폴더 이름을 위해 어차피 GPT를 한 번 부르므로 차이는 노트 100개당 몇 원 |

## 바뀌지 않는 것 (사용자가 보는 흐름)

- «분류하기» → **미리보기** → «옮기기» 두 단계와 화면
- 폴더 경로 규칙: 지금 폴더 기준 1~3층, 같은 경로는 한 폴더로 합침, 폴더 이름 규칙, 「미분류」 폴더
- 옮기기(`apply`): Blink의 `note:move`로 옮겨 링크가 따라 고쳐짐, 노트 하나가 실패해도 계속, 결과 보고
- 새 노트 자동 배치(처음 제목을 붙일 때 한 번)와 `.md` 끌어다 놓기의 시점
- 폴더 경로를 받아 검증하는 `planFolders`의 프롬프트·스키마·검증 — 묶음 하나를 노트 하나로 넘기면 그대로 쓸 수 있다

## 바뀌는 것 (안쪽)

| 지금 | 바뀐 뒤 |
| --- | --- |
| `embed()`로 제목 벡터 | 쓰지 않음 (OpenAI 어댑터의 `embed`는 남겨도 되고 지워도 됨) |
| `similarity.ts`, `kmeans.ts`, `clustering.ts`로 묶음 수·묶음 결정 | LLM이 노트마다 경로를 정함 |
| `placement.ts`의 반경 판정으로 «이미 있는 폴더에 맞는지» | LLM에게 기존 폴더 목록을 주고 «있는 폴더를 먼저 쓰라»고 함 |
| 실루엣 점수가 낮으면 «뚜렷한 묶음 없음» | «애매하면 「미분류」» 규칙을 프롬프트에 넣음 |
| 형제 폴더 노트를 새 묶음으로 끌어오기 | 빼거나 단순화 |
| 자동 배치: 층마다 내려가며 계산 | 폴더 나무 전체를 보여 주고 경로를 한 번에 고르게 함 |

## 구현할 때 함께 다룰 것

1. **폴더 수 조절** — 노트가 많을수록 잘게 나누는 경향(400개에서 폴더 56개). 노트 수에 맞춘 폴더 수 범위를 프롬프트에 준다.
2. **응답 길이** — 노트 수에 비례해 응답이 길어진다. 노트마다 경로를 쓰는 대신 «폴더 → 노트 번호 목록» 형태로 받으면 줄어든다.
3. **폴더 이름 오타** — 미리보기에서 이름을 고칠 수 있게 하거나, 프롬프트에 «기존 폴더 이름을 그대로 쓴다»를 넣는다.
4. **결과 일관성** — 같은 보관함을 다시 분류할 때 크게 바뀌지 않도록 기존 폴더를 우선한다.
5. 기존 폴더가 있는 상태, 애매한 노트가 많은 상태는 위 측정에 없다 — 구현 후 따로 시험한다.

## 측정 방법 (다시 재려면)

- **모델**: 채팅 `gpt-5.4-mini`(두 방식 공통), 임베딩 `text-embedding-3-large`(지금 코드 그대로). PR 시험 데이터 실험만 Kimi `kimi-k2.6`.
- **채팅 모델 방식**: 지금 코드의 `planFolders`에 노트 하나씩을 묶음으로 넘김(프롬프트·스키마 변경 없음).
- **임베딩 방식**: 지금 코드의 `OrganizeService.preview('')`를 임시 보관함에 그대로 실행.
- **데이터**: 주제 24개(코딩 6, 영어 2, 수학 1, 요리 4, 운동 3, 여행 3, 재테크 2, 독서 2, 업무 1) + 잡동사니 메모 약 12%. 주제마다 «대상 × 표현» 조합으로 제목을 만들고(예: `spring JPA 트러블슈팅`, `김치찌개 황금비율`), 주제 크기는 1~3배로 다르게. 시드 고정.
- **점수**: 순도(폴더마다 가장 많은 정답 주제의 비율), 역순도(정답 주제마다 가장 많이 모인 폴더의 비율), F1 = 둘의 조화평균. 순도만 보면 폴더를 잘게 나눌수록 높아지므로 역순도와 함께 본다.
- **멈춤 시간**: 전체 시간 − AI 호출(네트워크) 시간 = Main 프로세스에서 동기로 돈 계산 시간.
- 측정 스크립트는 임시로 썼고 저장소에는 두지 않았다. 실제 API 동작 확인은 `src/main/ai-provider/infrastructure/openai-provider.live.test.ts`(노트 100개 분류 포함)로 다시 돌릴 수 있다.
